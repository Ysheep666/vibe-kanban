Vibe Kanban's MCP server supports three launch modes. Each mode controls
how the server scopes its tool surface and how it behaves when an agent
launches from inside a VK worktree. Fresh installs default to
**Workspace** mode.

## Choosing a mode

<CardGroup cols={3}>
  <Card title="Workspace (default)" icon="folder-open">
  Auto-scopes to the VK worktree the agent was launched from. Exposes
  the full Global surface plus task orchestration
  (`create_task`, `create_and_start_task`, `list_tasks`, `get_task`,
  `update_task_status`, `delete_task`). Cross-scope mutations are
  rejected with `error_kind="scope_denied"`. Gracefully falls back
  to Global-equivalent behaviour when the CWD doesn't match a VK
  worktree.
  </Card>
  <Card title="Global" icon="globe">
  No CWD auto-scope. Every admin tool is available, but task
  orchestration tools are omitted (no ambient scope to default
  `parent_workspace_id` to). Use for admin scripts or CI.
  </Card>
  <Card title="Orchestrator" icon="robot">
  VK-internal only. A lean tool surface pinned to one parent task.
  Not user-facing.
  </Card>
</CardGroup>

## Launch args

<Tabs>
  <Tab title="Workspace (default)">
  ```json
  "args": ["-y", "vibe-kanban@latest", "--mcp", "--mode", "workspace"]
  ```
  </Tab>
  <Tab title="Global">
  ```json
  "args": ["-y", "vibe-kanban@latest", "--mcp", "--mode", "global"]
  ```
  </Tab>
</Tabs>

Orchestrator mode is not a user-facing launch option; VK's executor
framework uses it internally. Omitting `--mode` entirely uses the
Workspace default.

## Mode comparison

| Behaviour | Workspace | Global | Orchestrator |
|-----------|-----------|--------|--------------|
| CWD auto-scope to a VK worktree | Yes | No | Pinned to parent task |
| Cross-workspace mutations allowed | Rejected with a pointer to `--mode global` | Yes | No |
| Cross-repo mutations on scripts | Rejected with `error_kind="scope_denied"` | Yes | Rejected |
| Tool surface | Global admin tools + task orchestration | Admin tools only (no task orchestration) | Lean orchestrator surface |
| `create_task` / `create_and_start_task` | Yes | No | Yes |
| Intended caller | Coding agents launched inside VK worktrees | Admin scripts, CI, external MCP clients | VK-internal orchestration only |
| User-facing | Yes | Yes | No |

Workspace adds task orchestration on top of Global's admin surface and
enforces scope guards on workspace, repo, and task mutations. If a
mutation targets a workspace, repo, or task outside the current scope,
Workspace mode rejects it with `error_kind="scope_denied"` and a
message that points back to `--mode global` when cross-workspace admin
is genuinely required.

## Scope protection semantics

In Workspace mode (and Orchestrator), the MCP server tracks a *scoped
workspace ID* derived from the agent's current working directory, plus
a snapshot of that workspace's repo set.

- **Read tools** (`list_*`, `get_*`) never perform scope checks — an
  agent must be able to discover resources before operating on them.
- **Mutations that name a workspace ID** (for example
  `update_workspace`, `delete_workspace`,
  `link_workspace_issue`) are rejected unless the target is the
  scoped workspace or a descendant of it via the task parent-chain.
- **Mutations that name a repo ID** (`delete_repo`,
  `update_setup_script`, `update_cleanup_script`,
  `update_dev_server_script`) are rejected unless the repo is part of
  the scoped workspace's repo set. `add_repo` is not scope-guarded —
  it registers a new row and does not mutate any existing workspace.
- **Task orchestration tools** (`create_task`, `create_and_start_task`,
  `list_tasks`) default `parent_workspace_id` to the scoped workspace
  when omitted and reject an explicit parent that falls outside the
  scoped workspace or its descendant chain.
- **Mutations with implicit workspace** (session tools) inherit scope
  from the resource they act on.

If the agent's CWD doesn't match any VK worktree, Workspace mode
disables the scope check for that session — behaviour equivalent to
Global, except the task orchestration tools are still exposed.

## When does scope protection kick in?

Workspace-level mutations follow the parent-chain check:

```
AI calls a mutation with workspace_id = X
│
├─ Mode is Global? ──── allow (no scope)
│
├─ Mode is Workspace/Orchestrator ┐
│                                 │
│                    scoped_workspace_id is None? ─── allow (graceful fallback)
│                                 │
│                    X == scope? ─── allow (self)
│                                 │
│                    X's task.parent_workspace_id == scope? ─── allow (child)
│                                 │
│                                 └── reject with error_kind="scope_denied"
```

Repo-level mutations (`delete_repo`, `update_*_script`) use an
in-memory check against the scoped workspace's repo set:

```
AI calls a repo mutation with repo_id = R
│
├─ Mode is Global? ──── allow (no scope)
│
├─ Mode is Workspace/Orchestrator ┐
│                                 │
│                    scoped context is None? ─── allow (graceful fallback)
│                                 │
│                    R ∈ workspace_repos? ─── allow
│                                 │
│                                 └── reject with error_kind="scope_denied"
```

## Tool surface by mode

### Global

Global is the admin baseline. Every tool below is also exposed in
Workspace mode; Workspace adds task orchestration on top.

- **Context** — `get_context`
- **Workspaces** — `list_workspaces`, `update_workspace`,
  `delete_workspace`, `link_workspace_issue`
- **Workspace sessions** — `start_workspace`, `create_session`,
  `list_sessions`, `update_session`, `run_session_prompt`,
  `get_execution`, `read_session_messages`
- **Organisations** — `list_organizations`, `list_org_members`
- **Projects** — `list_projects`
- **Repositories** — `list_repos`, `get_repo`, `add_repo`,
  `delete_repo`, `update_setup_script`, `update_cleanup_script`,
  `update_dev_server_script`
- **Issues** — `list_issues`, `create_issue`, `get_issue`,
  `update_issue`, `delete_issue`, `list_issue_priorities`
- **Issue assignees** — `list_issue_assignees`, `assign_issue`,
  `unassign_issue`
- **Tags** — `list_tags`, `create_tag`, `update_tag`, `delete_tag`
- **Issue tags** — `list_issue_tags`, `add_issue_tag`,
  `remove_issue_tag`
- **Issue relationships** — `create_issue_relationship`,
  `delete_issue_relationship`

### Workspace

Workspace exposes everything Global does **plus** a task orchestration
surface:

- **Tasks** — `create_task`, `create_and_start_task`, `list_tasks`,
  `get_task`, `update_task_status`, `delete_task`

Mutations on workspaces, repos, and tasks are scope-guarded against
the current VK worktree. Task-tool parameters default to the scoped
workspace when omitted; see the full tool list and parameters in the
[Vibe Kanban MCP Server](/integrations/vibe-kanban-mcp-server)
reference.

### Orchestrator

Orchestrator pins a lean surface to a single parent task. It is only
launched by VK itself — end users do not configure this mode. The full
surface:

- **Context** — `get_context`
- **Workspaces** — `update_workspace`
- **Workspace sessions** — `create_session`, `list_sessions`,
  `read_session_messages`, `run_session_prompt`, `update_session`,
  `get_execution`
- **Tasks** — `list_tasks`, `get_task`, `create_task`,
  `create_and_start_task`, `update_task_status`, `delete_task`

## When to pick Global over Workspace

Choose Global when:

- You run admin scripts that touch multiple workspaces, repos, or
  scripts in one session.
- You drive CI jobs that need to create, list, or clean up resources
  across the whole organisation.
- You connect an external MCP client (Claude Desktop, Raycast) that is
  not launched from inside a VK worktree and only needs admin tools,
  not task orchestration.

In every other case — especially coding agents launched inside a VK
worktree — stick with Workspace mode. The scope guard is there to stop
an agent from accidentally mutating an unrelated workspace or repo,
and the task orchestration tools are only available in Workspace (or
Orchestrator) mode.
